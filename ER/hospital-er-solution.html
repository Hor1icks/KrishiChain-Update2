Task C - Assumptions

  1. Employee IDs are unique across all employee subtypes.
  2. The employee specialization is total and disjoint: every employee is exactly one doctor, nurse, or administrative staff member.
  3. Shift, specialization, and role are single-valued for an employee at the modeled time.
  4. A dependent name is unique only among one employee's dependents.
  5. A junior doctor has zero or one current supervisor; a senior doctor may supervise many junior doctors.
  6. A doctor cannot supervise themself.
  7. At most one consultation occurs for the same doctor and patient on one date; a timestamp or treatment ID would be needed otherwise.
  8. A prescription by the same doctor for the same patient and medicine is distinguished by prescription date.
  9. Each approved claim references exactly one treatment occurrence and one insurance company; unsubmitted or rejected treatments have no APPROVAL row.
  10. Amount approved is nonnegative, and age is calculated from date of birth rather than stored.

How to Convert a Scenario into an E-R Diagram and Schema

Use this checklist before drawing. First model the real-world meaning, then convert the finished E-R diagram into relations.

1. Find entities first

  • Entity = independent noun that needs stored facts: student, doctor, patient, medicine.
  • Strong entity has its own primary key.
  • Weak entity cannot be identified without an owner; mark partial key and identifying relationship.
  • Do not make every noun an entity. If it only describes another thing, it is probably an attribute.

2. Classify attributes

  • Simple: single stored value, like salary.
  • Composite: split into useful parts, like full_name = first_name + last_name.
  • Multivalued: many values for one entity, like phone_number; use double oval.
  • Derived: calculated from stored data, like age from date_of_birth; use dashed oval and do not store in schema.

3. Define relationships

  • Relationship = verb connecting entities: doctor treats patient.
  • Write cardinality beside each edge: 1, N, M, or optional/partial participation.
  • Put attributes on the relationship when the fact belongs to the event, not one entity.
  • Example: diagnosis belongs to a treatment event, not permanently to doctor or patient.

4. Identify ternary relationships

  • Use ternary when one fact needs three entities at the same time.
  • Test: if removing one entity changes the meaning, it is ternary.
  • Do not split into three binary relationships when the combination itself is the fact.
  • Example: doctor prescribes medicine to patient. Doctor-medicine alone and patient-medicine alone do not preserve who prescribed what to whom.

5. Identify aggregation

  • Use aggregation when a relationship occurrence must participate in another relationship.
  • Question to ask: is another entity acting on a whole event, not just one entity?
  • Use it when insurance approves a treatment, manager manages an employee-job-branch assignment, or department evaluates a student-project-supervisor assignment.
  • Do not aggregate if a normal entity is enough. If insurance approves only a patient, connect insurance to patient. If it approves a specific treatment event, aggregate treatment.

6. Convert E-R to schema

  1. Strong entity: create one table with its key and simple attributes.
  2. Composite attribute: store only components, not the parent attribute.
  3. Multivalued attribute: create a separate table with owner key + value as composite PK.
  4. Derived attribute: do not store it unless explicitly required.
  5. Weak entity: child table PK = owner PK + partial key; owner PK is also FK.
  6. 1:N relationship: put FK on the N-side table.
  7. M:N relationship: create a relationship table with both entity keys as FKs; add relationship attributes.
  8. 1:1 relationship: put FK on the total-participation side when possible.
  9. Ternary relationship: create one table containing all participating entity keys as FKs plus relationship attributes.
  10. Specialization: use parent + subclass tables for general cases; subclass PK is also FK to parent.
  11. Aggregation: map the inner relationship first, then reference its key from the outer relationship table.
Exam shortcut: underline every PK, mark every FK, draw every FK arrow toward the referenced PK, and write assumptions when a date/time or optional rule is not fully specified.
