KrishiChain — System Architecture

An agricultural supply-chain platform routing produce from farm to buyer through a virtual ARAT. Three tiers, one request path, and a database that is the final authority on every business rule.

Shape of the system

Three tiers, one direction of trust

Nothing below the browser trusts anything above it. The React app decides what to show; the API decides what a caller may do; the database decides what is legal. Each layer re-checks rather than inheriting the one above's word for it.

The signature path

One request, end to end

The clearest way to read this system is to follow a single call all the way down and back. Awarding a winning bid is the right one to trace: it is the demo centrepiece, it writes to four tables, and it must be all-or-nothing. A farmer clicks Award on a bid; nine hops later the batch is sold.

1Browser
BatchDetail.jsx → api('/farmer/batches/7/award', { method:'POST' })
client/src/pages/farmer/BatchDetail.jsx

The page never builds a URL containing the farmer's own id. It sends the batch and the bid only — who is asking is carried by the token, not the payload.

2Browser
api() attaches Authorization: Bearer <jwt>
client/src/api/client.js

One thin wrapper around fetch is the only place the token is read. It also converts any non-2xx response into a thrown Error carrying the server's own message, so no screen has to interpret status codes.

3Network
Vite dev server proxies /api/* → localhost:5000
client/vite.config.js

The client only ever uses relative paths, so there is no API host baked into the bundle.why 502 If the backend is not running, the proxy has nothing to reach and every call fails with 502 while the page itself loads perfectly.

4API
authenticate → requireRole('FARMER')
server/src/middleware/authenticate.js

The JWT is verified and becomes req.user. The role guard is applied once at the top of the router with router.use(…) rather than on each route, so a newly added endpoint cannot be left unguarded by accident.

5API
farmer.routes.js → farmer.awardBid(me(req), batchId, bidId)
server/src/routes/farmer.routes.js

Routes stay thin: read the request, call one service function, send the result, forward errors to next(). The helper me(req) resolves to req.user.userId — identity always comes from the verified token, never from the URL or body. That is what makes the ownership check below meaningful.

6API
withTransaction(async (connection) => { … })atomic
server/src/config/db.js

The service opens one explicit transaction: commit if the callback returns, roll back if it throws. oracledb.autoCommit is globally false, so this helper is the only way a multi-statement write reaches the database.

7Database
SELECT … FOR UPDATE → 4 writes on one connection
bid → WON · batch → SOLD · SALE_ORDER · TRANSPORT_REQUEST

The batch row is locked first so two farmers cannot award the same stock concurrently. Losing bids are bulk-updated to OUTBID in the same transaction. All four statements share one connection — that is what makes them one unit of work.

8Database
Constraints and triggers get the last wordauthority
database/01_create_tables.sql · 02_sequences_triggers.sql

Quantity ceilings, price floors and the one-active-bid rule are CHECK, UNIQUE and trigger logic in the schema, not just guards in JavaScript. A rule broken here raises ORA-20003 and the whole transaction unwinds, leaving nothing behind.

9API
errorHandler maps the outcome to a status
server/src/middleware/errorHandler.js

On success, JSON. On failure, an ApiError carries its own status, and any ORA-20000…20999 from a trigger becomes 422 with the trigger's own sentence — so a database rule reaches the user as readable text rather than a stack trace.

Every write path in the system has this same shape. What changes between them is only the number of statements inside step 6.

Tier one

Browser — React 19 + Vite

A single-page app with no server rendering and no state library. Screens fetch what they need on mount and hold it in local component state; the only shared state is the signed-in user.

AuthProvider

Holds the user, exposes login, register and logout. On refresh the token survives in localStorage but the user object does not, so it re-fetches /auth/me before rendering any route — without that, a signed-in user gets bounced to the login page on every reload.

src/context/AuthContext.jsx

ProtectedRoute

Redirects anonymous visitors to /login and wrong-role visitors to their own dashboard. Convenience, never security — the browser can be told anything, so the server re-checks the same rule on every request.

Tier two

API — Express on port 5000

A strict three-layer split. Routers know HTTP and nothing else; services know SQL and business logic and never touch req or res; config/db.js knows the connection pool and nothing about the domain.

Why start-up order matters

server.js awaits db.initialize() and only then calls app.listen(). Thick-mode initialisation must happen exactly once before any connection is opened; doing it lazily on the first request risks initOracleClient() racing itself under concurrent load. If the database is unreachable the process exits with a printed reason rather than starting and failing every call.

Three ways to reach the database

query()

One connection, one statement, released in a finally. Nothing here commits, so it is for SELECT only. Used by every list and dashboard endpoint.

withTransaction()

Commit on return, roll back on throw. The only sanctioned write path — 25 call sites across the six services. Fault-injection tested: a deliberately failing late statement must leave nothing behind.

callCursor()

Calls a PL/SQL procedure whose last argument is an OUT SYS_REFCURSOR and drains it in batches. The result set is closed explicitly — a ref cursor holds a server-side cursor open, and leaking them exhausts OPEN_CURSORS after a few hundred reports.

Error mapping

The status code carries meaning the client acts on. 422 is deliberately distinct from 400: the first means the rules forbid this, the second means you typed something wrong.

Tier three

Database — Oracle 11gR2 XE

The schema is the point of the project, not a persistence detail. It carries the graded ER constructs and it is the last line of enforcement for every business rule, so application code is written as a convenience layer over it rather than a gatekeeper in front of it.

28 tables

Built around five graded constructs: a total disjoint specialization of USERS, two aggregations, two ternary relationships, two weak entities and two recursive relationships.

19 sequences · 22 triggers

Constraints that shaped the build

Six decisions that are not obvious from the code

Each of these looks like an odd choice until you know what forced it. They are the questions most likely to be asked about this system.

node-oracledb must run in Thick mode

The driver's default Thin mode requires Oracle Database 12.1 or later and cannot reach 11.2 at all. initOracleClient() runs once at start-up against Instant Client 19c. On Linux the client is found through LD_LIBRARY_PATH, not the ORACLE_CLIENT_DIR variable in .env — that mechanism is Windows and macOS only.

Symptom when wrong: DPI-1047, whose message misleadingly blames an architecture mismatch.

autoCommit is globally false

Set once in config/db.js and never changed. An accidental autocommit would silently break the atomicity of all six workflows — the failure would not raise an error, it would just leave half-written data. Every write therefore has to go through withTransaction(), which is the point.

Payment rules live in a compound trigger

trg_payment_biz_rules enforces BR-19 by summing existing PAYMENT rows, which a row-level trigger on PAYMENT cannot do. BR-20 runs in BEFORE EACH ROW because it only reads other tables; BR-19 runs in AFTER STATEMENT.

Simplifying it back to a plain row trigger fails with ORA-04091: table is mutating.

Delivery is written before payment

In the delivery + payment workflow, TRANSPORT_REQUEST → DELIVERED must be written before the PAYMENT insert. The trigger reads TRANSPORT_REQUEST to enforce BR-20 and, inside one transaction, sees the uncommitted value.

Reverse the two statements and every on-delivery payment fails with ORA-20002.

Business rules are enforced in the schema, not only in JavaScript

Bid ≥ minimum price and > current highest, one active bid per buyer per batch, minimum price ≥ the crop's base price — all are CHECK, UNIQUE or trigger logic. Services re-check the same rules first purely to produce a friendlier message; the database is the backstop that cannot be bypassed by a direct API call.

Bind names are parsed as identifiers

A reserved word used as a bind variable breaks the statement before it runs, and the error names neither the column nor the offending word. Bind names are prefixed instead — :reviewComment, not :comment.

Symptom when wrong: ORA-01745, invalid host/bind variable name.
